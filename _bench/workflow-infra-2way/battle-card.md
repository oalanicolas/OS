## Strengths & Weaknesses

### workflow

**Strengths:**
- Event-sourced deterministic replay — the only side of this pair that can resume a long-running task mid-way after a cold start.
- Typed retry primitives (`FatalError` / `RetryableError` + programmable `retryAfter`) with default-3-retries semantics shipped out of the box.
- Pluggable `world` storage (local FS, Postgres, Vercel, in-memory testing) plus six first-party framework integrations (Next/Nitro/Nuxt/SvelteKit/Astro/Nest).

**Weaknesses:**
- JavaScript/TypeScript only — invisible to Python/Go/Rust teams.
- No built-in governance primitives: no safe-outputs-style validated-write layer, no secret redaction, no first-class approval gate.
- Production path is Vercel-native; self-host via Postgres exists but is less battle-tested.

### gh-aw

**Strengths:**
- Safety-by-default: AWF agent firewall, `safe-outputs` validated writes, SHA-pinned Actions, secret redaction, `on.manual-approval` via GitHub Environments, read-only default permissions.
- Markdown-as-DSL with multi-engine support (Copilot/Claude/Codex/Gemini/Crush) and 272 shipped sample workflows + 22 authoring skills.
- Zero new runtime — compiles to standard GitHub Actions YAML that runs on GitHub.com, GHES or self-hosted runners.

**Weaknesses:**
- No durable step persistence or deterministic replay — a re-run restarts the whole `workflow_run`.
- No typed retry controls for agent turns; retries delegated to Actions patterns + per-engine `max-turns`/`max-continuations` knobs.
- Tied to GitHub Actions runtime model; not portable to GitLab/Jenkins without adaptation. Pre-1.0 (v0.40.1), Spring-Break notice in README.

## When to pick workflow

You are building a long-running agent or a multi-step business flow in a JS/TS codebase that must survive cold starts, scale events and failures mid-task. You want durable primitives (steps, hooks, sleeps) with deterministic replay and typed retry controls, and you're already on Vercel or willing to stand up Postgres self-host.

## When to pick gh-aw

You want AI-driven automation of repo-centric tasks (triage, PR review, docs upkeep, maintenance) that runs where your code already lives — GitHub Actions — with hard safety rails (read-only defaults, validated writes, AWF firewall, approval gates) and the freedom to route through any of Copilot/Claude/Codex/Gemini. The workflow source should read like prose and ship as a `.md` file to a marketplace.

## TL;DR Verdict

These tools aren't really competitors — they solve different problems: workflow is durable-function infrastructure for JS apps; gh-aw is a safety-focused agentic CI layer on top of GitHub Actions. The scorecard tilts to workflow (77.08 vs 58.20) because the chosen pack (workflow-infra) weights durability/event-log/retries — workflow's home turf. On the governance axis (safe-outputs, redaction, approval gates), gh-aw is clearly ahead and workflow could absorb several low-complexity wins (see gap-analysis GAP-A-003, A-005, A-006).

**Recommendation:** use both. Pick workflow when you need durable execution; pick gh-aw when you need safe agentic CI. They compose: gh-aw can trigger workflow runs for durable sub-tasks, and workflow can surface results through gh-aw's safe-outputs on pull requests.
